# Intake order

One persistent project per client. Material goes in by kind, in this order. Each source gets its inventory row before you read it for content.

## 1. Records and decisions

Registries, decision logs, objective pages, policies, org charts, contract lists. The client already treats these as true. A finding that contradicts one needs stronger evidence than a finding that confirms one. Read them first so you read every later source against them.

Through MCP: read the live page and note the last-edited date in the inventory. A page last edited two quarters ago is itself a finding.

## 2. Interviews

One transcript per session. The same day, write a client-safe summary: function, what they described, the finding candidates it supports, the quotes to keep. The summary goes in the appendix. The transcript does not. On the first run, thirteen interviews became one appendix file of summaries.

Recorder: Kept or Otter for calls you host. Ask for the recording when the client hosts. Mark any transcript that was not checked against audio.

## 3. Chat and working documents

Slack, Drive, working Notion pages, ticket queues. Use them to confirm or contradict candidates from steps 1 and 2, and to find where a decision left the record. Do not start here. A synthesis that starts in chat comes out as a list of complaints.

## MCP reads, exports, and transcripts

| Channel | Currency | Inventory note |
|---|---|---|
| MCP read of a live workspace | Current at read time | Record the read date and whether the read was a sample or the whole space |
| Export (zip, CSV, PDF) | Stale from the export date | Record the export date. Re-request before the final draft |
| Transcript | Fixed | Record whether it was checked against audio |
| Registry or automated discovery data | Counts one population | Record the population. Without it the counts read as contradictions |

On the first run, most material came in by MCP and by call transcript. One requested export never arrived. The inventory carried that as a limit from the week it was due. The deliverable said what stayed open because of it.

## The persistent project

Keep everything for one client in one place the model can see across sessions: the inventory, the candidates list, the summaries, the table. Files do not update themselves. Use the inventory's date columns to decide what to refresh before a draft.
