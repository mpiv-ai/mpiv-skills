# Intake order

One persistent project per client. Material goes in by kind, in this order, and each source gets its inventory row before it is read for content.

## 1. Records and decisions

Registries, decision logs, objective pages, policies, org charts, contract lists. These are what the client already treats as true, so a finding that contradicts one needs stronger evidence than a finding that confirms one. Read them first so every later source is read against them.

Through MCP: read the live page, note the last-edited date in the inventory. A page last edited two quarters ago is a finding in itself.

## 2. Interviews

One transcript per session. The same day, write a client-safe summary: function, what they described, the finding candidates it supports, the quotes worth keeping. The summary goes in the appendix; the transcript does not. Thirteen interviews on the first run produced one appendix file of summaries.

Recorder notes: Kept or Otter for calls you host; ask for the recording when the client hosts. Mark a transcript that was not re-listened as such.

## 3. Chat and working documents

Slack, Drive, working Notion pages, ticket queues. Wide and shallow. Use them to confirm or contradict candidates from steps 1 and 2, and to find the moment a decision left the record. Do not start here; a synthesis that starts in chat produces a list of complaints.

## MCP reads, exports, and transcripts

| Channel | Currency | Inventory note |
|---|---|---|
| MCP read of a live workspace | Current at read time | Record the read date and whether the read was a sample or full |
| Export (zip, CSV, PDF) | Stale from the export date | Record the export date; re-request before the final draft |
| Transcript | Fixed | Record whether it was reviewed against audio |
| Registry or automated discovery data | Counts a specific population | Record the population, or the counts will be read as contradictions |

On the first run, most material came in by MCP and by call transcript. One requested export never arrived; the inventory carried that as a limit from the week it was due, and the deliverable said what stayed open because of it.

## The persistent project

Keep everything for one client in one place the model can see across sessions: the inventory, the candidates list, the summaries, the table. Files do not update themselves; the inventory's date columns are how you know what to refresh before a draft.
